## 1. 概要

### 1.1 背景
手持ちの洋服が増えると、何を持っているか・いつどこで買ったかを把握しづらくなり、似た服を重複して購入したり、持っている服を活用しきれなかったりする。既存のクローゼット管理サービスはSNS機能やEC連携など多機能なものが多く、自分の服を写真付きでシンプルに記録する用途に特化したツールが少ない。

### 1.2 目的
自分が所有する洋服を写真・ブランド・サイズ・購入情報・季節・素材などの情報とともにiPhoneで手軽に登録し、一覧から絞り込み・並び替えを行って手持ちの服をすぐに把握できるWebアプリケーションを提供する。

## 2. 対象範囲（スコープ）

### 2.1 対象とする範囲
- 洋服（アイテム）の登録・一覧表示・詳細表示・編集・削除
- iPhoneのカメラ撮影またはフォトライブラリからの写真登録（1アイテムにつき1枚以上、複数枚可）
- アイテム一覧の絞り込み（カテゴリ・サブカテゴリ・色・季節・ブランド）および並び替え
- サブカテゴリの管理（初期サブカテゴリの提供＋ユーザーによる追加・編集・削除・並び替え）

### 2.2 対象外とする範囲
- ユーザー登録・ログイン等の認証機能（自分専用・端末内利用のため不要）
- 複数ユーザーでの利用、他者とのデータ共有・SNS的機能
- iPhone以外の端末（Android端末、PC）での利用を前提とした設計・動作保証
- 複数端末間のデータ同期・クラウドへのデータ保存
- データのバックアップ（エクスポート）および復元（インポート） ※将来検討（制約事項 7章参照）
- カテゴリ（大分類）の追加・編集・削除（カテゴリはシステムで固定とする）
- レディース衣料を想定したカテゴリ・サブカテゴリの提供（本フェーズはメンズを想定する）
- コーディネート（アイテムの組み合わせ）管理 ※将来検討
- 着用記録（着用日・着用回数の記録） ※将来検討
- 統計・分析機能（カテゴリ別点数、購入金額合計、未着用アイテムの抽出等） ※将来検討
- 画像からのアイテム情報自動認識、背景除去等の画像加工
- ECサイト・購入履歴との連携
- ネイティブアプリ（iOS）としての提供

## 3. 用語定義

| 用語 | 説明 |
|------|------|
| アイテム | ユーザーが所有する洋服・靴・小物など1点ごとの登録データ。写真および属性情報（カテゴリ・色・ブランド等）を持つ |
| カテゴリ | アイテムの種類を表す大分類（例: トップス、ボトムス、アウター）。システムで固定とし、ユーザーは変更できない |
| サブカテゴリ | カテゴリをさらに細かく分けた小分類（例: ボトムス → スラックス、デニム、カーゴパンツ）。ユーザーが追加・編集・削除できる |
| ベースカラー | アイテムの主となる色。1アイテムにつき1色を設定する |
| 代表写真 | アイテムに登録された写真のうち、一覧のサムネイルに表示する1枚 |
| 季節 | アイテムの着用シーズン（春・夏・秋・冬）。1アイテムに複数設定可能 |
| PWA | Progressive Web App。ブラウザで動作し、ホーム画面への追加やオフライン動作が可能なWebアプリケーション |

| BR-001 | 所有する洋服の記録 | ユーザーは所有する洋服を写真と属性情報とともに記録できること |
| BR-002 | 所有する洋服の把握 | ユーザーは記録した洋服を一覧・絞り込みで素早く確認し、重複購入の防止やコーディネート検討に役立てられること |
## 5. 機能要件

### 5.1 機能一覧

| ID | 機能名 | 概要 | 優先度 |
|----|--------|------|--------|
| FR-001 | アイテム登録 | 写真と属性情報（5.2参照）を入力してアイテムを登録する。写真はカメラ撮影またはフォトライブラリから選択でき、1枚以上の登録を必須とする | 高 |
| FR-002 | アイテム一覧表示 | 登録したアイテムを代表写真のサムネイルによるグリッド形式で一覧表示する | 高 |
| FR-003 | アイテム詳細表示 | 選択したアイテムの全写真（スワイプで切り替え）と全属性情報を表示する | 高 |
| FR-004 | アイテム編集 | 登録済みアイテムの属性情報を変更し、写真の追加・削除・代表写真の変更を行う（写真は1枚以上残すこと） | 高 |
| FR-005 | アイテム削除 | 登録済みアイテムを削除する（削除前に確認を行う） | 高 |
| FR-006 | 絞り込み・並び替え | 一覧をカテゴリ・サブカテゴリ・ベースカラー・季節・ブランドで絞り込み、登録日・購入日・購入金額・名前で並び替える | 中 |
| FR-007 | サブカテゴリ管理 | カテゴリごとに初期サブカテゴリ（5.3参照）を提供し、ユーザーがサブカテゴリを追加・名称変更・削除・並び替えできる | 中 |
### 5.2 アイテムの管理項目

| 項目 | 必須 | 入力形式 | 備考 |
|------|------|---------|------|
| 写真 | 必須 | 画像（カメラ撮影／フォトライブラリ選択）。1枚以上、最大10枚 | 1枚目を代表写真とし、任意の写真を代表写真に変更できる。最大枚数は暫定値 |
| 名前 | 必須 | テキスト | 例: 白の無地Tシャツ |
| カテゴリ | 必須 | 選択（5.3の固定カテゴリから1つ） | |
| サブカテゴリ | 任意 | 選択（選択したカテゴリに属するサブカテゴリから1つ） | カテゴリを変更した場合は未選択に戻す |
| ベースカラー | 必須 | 選択（既定の色リストから1つ） | 色リストは基本設計で定義する（例: 白、黒、グレー、ネイビー、ベージュ、ブラウン、赤、青、緑、黄、ピンク、紫、その他） |
| ブランド | 任意 | テキスト（過去の入力値から候補表示） | |
| サイズ | 任意 | テキスト | S/M/L、数値表記など自由入力 |
| 購入日 | 任意 | 日付 | |
| 購入金額 | 任意 | 数値（円） | |
| 購入店舗 | 任意 | テキスト | |
| 季節 | 任意 | 複数選択（春・夏・秋・冬） | |
| 素材 | 任意 | テキスト | 例: 綿100% |
| 洗濯方法 | 任意 | テキスト | 例: 手洗い、クリーニング |
| メモ | 任意 | テキスト（複数行） | |
| 登録日時・更新日時 | ― | 自動設定 | 画面入力なし |

### 5.3 カテゴリおよび初期サブカテゴリ
本フェーズではメンズ衣料の管理を想定し、カテゴリは以下で固定とする。サブカテゴリは初期値として以下を提供し、ユーザーが自由に追加・編集・削除できる。

| カテゴリ（固定） | 初期サブカテゴリ（編集可） |
|----------------|------------------------|
| トップス | Tシャツ（半袖）、Tシャツ（長袖）、シャツ（半袖）、シャツ（長袖）、ポロシャツ、ニット・セーター、スウェット、パーカー、タンクトップ |
| ボトムス | スラックス、デニム、チノパン、カーゴパンツ、ワイドパンツ、イージーパンツ、ショートパンツ |
| アウター | テーラードジャケット、ブルゾン、レザージャケット、コート、ダウンジャケット、カーディガン、ベスト |
| セットアップ・スーツ | セットアップ、スーツ |
| シューズ | スニーカー、革靴、ブーツ、ローファー、サンダル |
| バッグ | リュック、ショルダーバッグ、トートバッグ、ボディバッグ、ビジネスバッグ |
| 帽子 | キャップ、バケットハット、ハット、ニット帽 |
| アクセサリー・小物 | ベルト、ネクタイ、マフラー・ストール、手袋、腕時計、財布、アクセサリー |
| その他 | （なし） |

- トップスのTシャツ・シャツは、半袖と長袖を別のサブカテゴリとして区別する
- サブカテゴリの名称は同一カテゴリ内で重複不可とする
- アイテムが設定されているサブカテゴリは削除不可とする（暫定。将来見直しの可能性あり）
- 初期サブカテゴリの具体的な内容は基本設計で確定する

## 6. 非機能要件

| 分類 | 要件 |
|------|------|
| 対応端末 | iPhoneのSafari（最新のiOSおよびその1つ前のメジャーバージョン）。縦画面での片手操作を前提とする |
| 利用形態 | ホーム画面に追加してアプリのように起動できること（PWA）。通信圏外でも全機能が利用できること |
| 性能 | 想定所有点数は当面50〜100点とする。将来の増加を見込み、アイテム300件登録時に一覧表示・絞り込みの結果表示が2秒以内であること |
| 容量 | 写真は登録時に端末上で縮小・圧縮（長辺1280px程度）し、端末の保存容量を圧迫しないこと（目安: 100点×平均3枚で100MB程度以内） |
| セキュリティ | 認証機能は設けない。データは利用者の端末内にのみ保存し、外部サーバーへ送信しないこと |
| 可用性・データ保全 | 本フェーズではバックアップ・復元機能を提供しない。データの自動削除を避けるため、ブラウザに永続ストレージの利用を要求すること（Storage API の persist）。将来バックアップ・復元機能を追加できるよう、データ構造は書き出し可能な形で設計すること |
| 保守性 | 個人開発で継続的に保守できるよう、広く普及した技術を採用し、構成をシンプルに保つこと |

## 7. 制約事項
- 個人開発であり、開発・運用リソースが限定される
- 運用費用は原則無料とする（無料のホスティングサービスの範囲内で運用する）
- データはiPhoneのブラウザ内ストレージに保存するため、以下の制約がある
  - 端末間でのデータ共有はできない。また、本フェーズではバックアップ・復元機能を提供しないため、機種変更時にデータを移行できない
  - Safariの履歴・Webサイトデータの削除、端末の故障・紛失・初期化によりデータが失われた場合、復旧できない（利用者はこのリスクを受容する）
  - iOS Safariでは、ホーム画面に追加せずに利用し一定期間アクセスしない場合、データが自動削除される可能性があるため、ホーム画面に追加して利用することを前提とする

## 8. 前提条件
- 利用者は本人1名のみである
- 利用者はカメラ付きのiPhoneを所有している
- アプリの初回読み込み時およびアップデート時のみインターネット接続を必要とする

## 9. 技術選定
要件（iPhoneのみ・端末内利用・認証なし・運用費無料）を踏まえ、サーバーを持たずにブラウザ内で完結する以下の構成を採用する。ライブラリのバージョン等の詳細は基本設計フェーズで確定する。

| 区分 | 採用技術 | 選定理由 |
|------|--------|---------|
| アプリ形態 | PWA（静的Webアプリ） | ネイティブアプリ不要でホーム画面追加・オフライン動作・カメラ利用が可能。App Store申請も不要 |
| フロントエンド | TypeScript + React + Vite | 普及度が高く情報が豊富。型によりデータ構造の変更に強い |
| データ保存 | IndexedDB（ラッパーライブラリ: Dexie.js） | ブラウザ内で写真（Blob）を含む大容量データを保存でき、検索・並び替え用のインデックスも作成可能 |
| PWA対応 | vite-plugin-pwa（Service Worker） | オフラインキャッシュとホーム画面追加の設定を簡易に実現できる |
| 画像処理 | Canvas APIによる縮小・JPEG圧縮 | 追加ライブラリなしで端末上で圧縮でき、外部送信が不要 |
| ホスティング | GitHub Pages 等の無料静的ホスティング | サーバー運用不要・無料。配信するのはアプリ本体のみで、利用者のデータはサーバーに置かれない |

※ 比較検討した代替案
- 前回の読書記録アプリと同様の Spring Boot ＋ DB サーバー構成：iPhone単体で利用するにはサーバーを常時稼働・公開する必要があり、その場合は認証も必須となるため、今回の要件では過剰と判断
- ネイティブアプリ（Swift、Flutter等）：開発・配布の手間（Apple Developer Program登録等）が大きく、個人利用には過剰と判断
