## 2. 合意事項一覧

### 2.1 要件定義

| ID | 項目 | 合意内容 | 理由・経緯 | 記載先 |
|----|------|---------|-----------|--------|
| K-01 | 利用者・認証 | 本人専用。ユーザー登録・ログインは設けない | 自分専用で端末内のみで使うため認証は不要 | 要件定義書 2章 |
| K-02 | 対象端末 | iPhoneのSafariのみ（Android・PCは対象外） | 当初「スマホ・PC両方」→「スマホのみ」→「iPhone」と段階的に確定（2.6 C-01） | 要件定義書 6章 |
| K-03 | データの保存先 | iPhoneのブラウザ内にのみ保存し、外部サーバーへ送信しない | ローカル利用・ログインなしの要件を、サーバーなしで満たすため | 要件定義書 6・7章 |
| K-04 | 必須機能 | 写真付きのアイテム登録・一覧・詳細・編集・削除、絞り込み・並び替え、サブカテゴリ管理 | コーディネート管理・着用記録・統計は将来検討とした | 要件定義書 2・5章 |
| K-05 | 管理項目 | 写真・名前・カテゴリ・サブカテゴリ・ベースカラー・ブランド・サイズ・購入日・購入金額・購入店舗・季節・素材・洗濯方法・メモ | 必須は写真・名前・カテゴリ・ベースカラー | 要件定義書 5.2 |
| K-06 | 写真 | 1アイテムにつき1枚以上必須、複数枚可（最大10枚）。先頭を代表写真とする | 最大10枚は暫定値として設定し、その後の設計で採用 | 要件定義書 5.2 |
| K-07 | 色 | 主となる色（ベースカラー）を1色だけ設定する。既定の14色から選ぶ | 複数色の管理は不要と判断 | 要件定義書 5.2、SC-05 |
| K-08 | 想定点数・性能 | 当面50〜100点。300件で一覧表示・絞り込みが2秒以内 | 将来の増加を見込んだ目標値 | 要件定義書 6章 |
| K-09 | カテゴリ | カテゴリは固定9種。サブカテゴリはユーザーが追加・名称変更・削除・並び替えできる | 当初「カテゴリを追加可能」だったが、固定＋サブカテゴリ編集に変更（2.6 C-03） | 要件定義書 5.3 |
| K-10 | カテゴリの内容 | メンズ向けに定義。Tシャツ・シャツは半袖と長袖を別のサブカテゴリにする | 利用者がメンズのため | 要件定義書 5.3 |
| K-11 | サブカテゴリの削除 | アイテムが登録されているサブカテゴリは削除不可 | 暫定仕様として合意 | 要件定義書 5.3 |
| K-12 | バックアップ・復元 | 本フェーズではスコープ外（将来検討） | 一度追加したが除外（2.6 C-02）。機種変更・データ削除時にデータを失うリスクは利用者が受容 | 要件定義書 2.2・7章 |
| K-13 | 検索 | 絞り込み・並び替えあり。キーワード検索は設けない | 一覧のチップと絞り込みで十分と判断 | 要件定義書 2.1、画面定義書 7章 |

### 2.2 技術選定

| ID | 区分 | 合意内容 | 理由 |
|----|------|---------|------|
| K-20 | アプリ形態 | PWA（ホーム画面に追加して使う静的Webアプリ） | ネイティブアプリ不要でオフライン動作・カメラ利用が可能。App Store申請も不要 |
| K-21 | フロントエンド | TypeScript + React + Vite | 普及度が高く情報が多い。型によりデータ構造の変更に強い |
| K-22 | データ保存 | IndexedDB（Dexie.js） | 写真を含む大容量データをブラウザ内に保存でき、検索用の索引も作れる |
| K-23 | 画像処理 | 端末上で長辺1280px程度に縮小・JPEG圧縮。一覧用の小さい画像も作成 | 保存容量の節約。外部送信が不要 |
| K-24 | ホスティング | GitHub Pages 等の無料静的ホスティング | 運用費無料。配信するのはアプリ本体のみで利用者のデータはサーバーに置かれない |
| K-25 | 不採用案 | Spring Boot＋DBサーバー構成、ネイティブアプリ | サーバー公開・認証が必要になる、または開発・配布の手間が大きく、今回の要件には過剰 |

※ iOS Safariはホーム画面に追加せずに使うと、しばらく開かない間にデータが自動削除される場合がある。そのため「ホーム画面に追加して使う」ことを前提とし、未追加時は一覧に案内バナーを出す。

### 2.6 主な変更の経緯

| ID | 変更内容 | 変更前 | 変更後 | 理由 |
|----|---------|--------|--------|------|
| C-01 | 対象端末 | スマホ・PC両方 | スマホのみ → iPhoneのみ | 利用者の判断。ローカル利用・ログインなしの方針とも整合 |
| C-02 | バックアップ・復元 | 機能要件（FR-008/009）として追加 | スコープ外 | 利用者の判断で一旦対象外とし、データ消失リスクを受容 |
| C-03 | カテゴリ管理 | 初期カテゴリ＋ユーザーが追加可能 | カテゴリは固定、サブカテゴリをユーザーが編集 | 大分類はシステムで統一し、細分類だけ自由にしたいため |
| C-04 | カテゴリ内容 | 男女共通の汎用的な内容 | メンズ向けに再定義、Tシャツ・シャツの半袖／長袖を区別 | 利用者がメンズのため |
| C-05 | 文書名 | 画面設計書 | 画面定義書 | 内容（画面一覧・項目・遷移の定義）に合わせた名称 |
| C-06 | 画面詳細設計書の構成 | 1ファイルに全画面 | 画面単位でファイルを分割 | 画面単位でのレビュー・改訂をしやすくするため |
| C-07 | 前回プロジェクトの設計書 | `02_design/02_detailed/` に読書記録アプリの設計書が残存 | すべて削除（テンプレートは残す） | 本プロジェクトと無関係のため。git履歴から復元は可能 |
| C-08 | 処理設計書の構成 | 1ファイルに全処理 | 処理単位でファイルを分割（共通事項は `00_共通.md`） | 画面詳細設計書と同様に、処理単位でのレビュー・改訂をしやすくするため |
| C-09 | DB設計書の構成 | 1ファイルに全テーブル | テーブル単位でファイルを分割（共通事項・ER図は `DB設計書/00_共通.md`） | 画面・処理と同様に、テーブル単位でのレビュー・改訂をしやすくするため |

## 3. 文書作成のルール

| ID | ルール |
|----|-------|
| R-01 | 各文書の冒頭に作成日・作成者・版数・関連文書を記載し、改訂時は版数を上げて改訂履歴に追記する |
| R-02 | 要件・設計で不明点や判断が必要な点がある場合は、作業を進める前に利用者へ確認する |
| R-03 | 自分で新たに決めた仕様は、各文書末尾の「確認事項」に記載し、利用者の合意を得てから確定とする |
| R-04 | 「画面設計書」ではなく「画面定義書」と呼ぶ。画面定義書には画面遷移図を含める |
| R-05 | 図は draw.io 形式（`.drawio`）を原本とし、Markdownで表示するための `.png` を併せて保存する。修正時は原本を直してPNGを書き出し直す |
| R-06 | 画面詳細設計書は画面単位でファイルを分ける（ファイル名は「画面ID_画面名.md」）。全画面共通の仕様は `00_共通仕様.md` にまとめる |
| R-07 | 画面詳細設計書には寸法（余白・文字サイズ・部品の大きさ等）を記載しない。見た目はモックを参考に実装時に調整する |
| R-08 | ダイアログ・シートのうち補助的なもの（DL-xx）は、表示元の画面のファイルに記載する |
| R-09 | メッセージの文言は `00_共通仕様.md` のメッセージ一覧で一元管理し、各画面からはIDで参照する |
| R-10 | 作業は区切り（画面のまとまり）ごとに利用者のレビューを受け、合意を得てから次へ進む |
| R-11 | 用語は要件定義書の用語定義（アイテム・カテゴリ・サブカテゴリ・ベースカラー等）に統一する |
| R-12 | 処理設計書は処理単位でファイルを分ける（ファイル名は「処理ID_処理名.md」）。構成・例外処理・ログなど全処理共通の方針は `00_共通.md` にまとめる |
| R-13 | 設計書は原則として1つの大きなファイルにまとめず、画面・処理・テーブルなどの単位で分割する |
| R-14 | DB設計書はテーブル単位でファイルを分ける（ファイル名は「テーブルID_テーブル名.md」）。前提・ER図・コード定義・トランザクションなど全テーブル共通の内容は `00_共通.md` にまとめる |
