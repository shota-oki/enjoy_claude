## 1. 概要
アプリをビルドして公開先に配置する手順と、版数の付け方、公開先の選び方を定める。リリース作業の具体的な手順は、実装後に `docs/04_release/リリース手順書.md` にまとめる。

## 2. 公開先

| 候補 | 費用 | 条件・特徴 |
|------|------|-----------|
| GitHub Pages | 無料 | 無料プランでは**公開（public）リポジトリのみ**利用できる。非公開リポジトリで使うには有料プランが必要 |
| Cloudflare Pages | 無料 | 非公開リポジトリでも無料で利用できる。GitHub と連携して自動公開できる |

- 要件定義書では「GitHub Pages 等の無料静的ホスティング」としている。リポジトリを公開してよい場合は GitHub Pages、非公開のままにしたい場合は Cloudflare Pages を使う
- いずれの場合も、公開先に置くのはアプリ本体のファイルのみで、利用者のデータは置かれない
- リポジトリを公開にした場合、設計書（`docs/`）も誰でも閲覧できる状態になる（設計書に個人情報は含めない）

公開URL（GitHub Pages の場合）：`https://shota-oki.github.io/enjoy_claude/`

## 3. 版数の付け方
`package.json` の版数を「メジャー.マイナー.パッチ」の形式で管理する。この版数は SC-06 の「バージョン」に表示する。

| 区分 | 上げるとき | 例 |
|------|-----------|----|
| メジャー | DB構造の大きな変更など、利用者への影響が大きい変更 | 1.0.0 → 2.0.0 |
| マイナー | 機能の追加・変更 | 1.0.0 → 1.1.0 |
| パッチ | 不具合の修正、文言の修正 | 1.0.0 → 1.0.1 |

- 最初に公開する版は 1.0.0 とする

## 4. 自動化（GitHub Actions）

### 4.1 検査（main への取り込み時・作業ブランチへの push 時）
1. 依存パッケージをインストールする（`npm ci`）
2. `npm run lint`、`npm run typecheck`、`npm run test` を実行する
3. いずれかが失敗した場合は、取り込みを行わない

### 4.2 公開（版のタグを付けたとき）
main ブランチの公開したいコミットに `v1.0.0` のような版のタグを付けると、以下を自動で行う。
1. 4.1 の検査をすべて実行する
2. タグと `package.json` の版数が一致することを確認する
3. `npm run build` でビルドする（公開URLに合わせたパスを設定）
4. 公開先にビルド結果を配置する
5. 失敗した場合は公開を中止し、それまでの版が公開されたまま残る

- main に取り込むたびに公開しないのは、公開のたびに利用者に更新の案内（M-01 4章）が出るため。まとまった単位でタグを付けて公開する

## 5. 公開後の確認と切り戻し
- 公開後、iPhone のアプリで更新の案内が出ること、更新後に SC-06 の版数が新しくなっていること、既存のデータが表示されることを確認する
- 公開した版に不具合があった場合は、直前の版のタグで公開をやり直す（公開処理を手動で再実行する）。ただし DB構造を変えた版のあとは前の版に戻せないため、修正版を公開する（M-01 5章）
