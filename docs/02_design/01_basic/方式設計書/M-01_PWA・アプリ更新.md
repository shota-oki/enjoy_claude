## 1. 概要
アプリをiPhoneのホーム画面に追加して使えるようにし、通信がなくても起動でき、新しい版を公開したときに安全に切り替わるための仕組みを定める。

## 2. ホーム画面に追加したときの設定

### 2.1 アプリ情報（マニフェスト）

| 項目 | 設定値 | 説明 |
|------|-------|------|
| アプリ名（name） | 洋服管理 | アプリの正式名 |
| ホーム画面の表示名（short_name） | クローゼット | ホーム画面のアイコンの下に表示される名前。iPhoneでは長いと省略されるため6文字程度 |
| 表示方法（display） | standalone | Safariのアドレスバー等を表示せず、アプリのように全画面で表示する |
| 画面の向き（orientation） | portrait | 縦画面のみ |
| 開始URL・範囲（start_url・scope） | アプリの公開URL（M-03） | |
| テーマ色（theme_color） | #2B5F8E（ネイビー系） | アクセントカラーと同じ |
| 背景色（background_color） | #F2F2F7 | 起動中の画面の背景 |
| アイコン | 180×180（iPhone用）、192×192、512×512 のPNG | デザインは実装時に作成する |

### 2.2 iPhone向けの追加設定
- iPhoneはマニフェストのアイコンを使わない場合があるため、`apple-touch-icon`（180×180）を別途指定する
- ホーム画面から起動したときの上部の表示（時刻・電池等）は、画面の背景に合わせた表示とする
- 画面の切り欠き（ノッチ）やホームバーの部分に操作部品が重ならないよう、安全領域（safe area）を考慮した配置とする

## 3. オフライン動作
- vite-plugin-pwa で Service Worker を生成する
- ビルドで作られたアプリ本体のファイル（HTML・JavaScript・CSS・アイコン）はすべて、初回の読み込み時に iPhone 内に保存（事前キャッシュ）する
- 2回目以降の起動では、通信の有無にかかわらず iPhone 内に保存したファイルから起動する
- アプリが外部から取得するデータはないため、事前キャッシュ以外のキャッシュは設けない
- 利用者のデータは IndexedDB に保存しており、Service Worker のキャッシュとは別の領域である（キャッシュを更新・削除してもデータは消えない）

## 4. 新しい版への切り替え

### 4.1 方式
新しい版を公開したら、アプリ内に案内を表示し、利用者が「更新」を押したときに切り替える方式とする。

| 方式 | 内容 | 採否 |
|------|------|------|
| 案内を表示して利用者が切り替える | 新しい版を検知したら案内を出し、「更新」を押すと再読み込みして切り替える | 採用 |
| 自動で切り替える | 新しい版を検知したら即座に再読み込みする | 不採用。登録フォームの入力中に再読み込みされると入力内容が失われるため |
| 次回起動時に切り替える | 案内は出さず、アプリを完全に閉じて開き直したときに切り替える | 不採用。iPhoneはホーム画面のアプリを完全に閉じないことが多く、古い版が使われ続けるため |

### 4.2 新しい版の確認タイミング
- アプリの起動時
- アプリが前面に戻ったとき（他のアプリから切り替えて戻ったとき）。ただし前回の確認から1時間以上経っている場合のみ
- 通信できない場合は確認しない（古い版のまま動作を続ける）

### 4.3 案内の表示
- 新しい版を検知したら、画面下部（タブバーの上）に案内を表示する：「新しいバージョンがあります」＋「更新」ボタン
- 案内は利用者が「更新」を押すか、×で閉じるまで表示し続ける。×で閉じた場合は、次の確認タイミングで再度表示する
- SC-05（登録・編集）の表示中は案内を出さず、SC-05 を閉じたあとに表示する（入力中の誤操作を防ぐため）
- 「更新」を押したら、新しい版に切り替えてアプリを再読み込みし、SC-01 を表示する

※ この案内は画面詳細設計書にない新しい表示部品のため、本書の合意後に画面詳細設計書 共通仕様（共通部品・メッセージ一覧）に追加する。

## 5. データ構造の移行
- 新しい版でDBの構造を変える場合は、DB設計書 共通 9章のとおり Dexie.js のバージョンを上げ、移行処理を記述する
- 移行処理は、新しい版の起動時（処理設計書 P-01 の手順1「DBを開く」）に自動で1回だけ実行される
- 移行処理は、それまでに公開したすべての版のデータから移行できるように書く（利用者が何版か飛ばして更新する場合があるため）
- 古い版に戻す（ダウングレード）ことは想定しない。DB構造を変える版を公開したあとに問題が見つかった場合は、修正版を新たに公開して対応する
- DB構造を変える版は、公開前に「旧版のデータを入れた状態からの更新」をテストする（テスト方針書）
