## 1. 目的・対象
洋服管理アプリが要件定義書と各設計書のとおりに動作し、iPhone で安心して使える品質であることを確認するための、テストの進め方を定める。個々のテストケースは、本書に従って各テストレベルの仕様書（`docs/03_test/` 配下のテンプレート）に記載する。

| 対象 | 範囲 |
|------|------|
| テスト対象 | アプリ本体（`app/`）の全機能、PWA としての動作（ホーム画面追加・オフライン・更新）、非機能要件 |
| 対象外 | 公開先（GitHub Pages 等）そのものの動作、iOS・Safari の不具合 |

## 2. テストレベル

| レベル | 目的 | 対象 | 方法 | 実施時期 | 仕様書・結果 |
|-------|------|------|------|---------|-------------|
| 単体テスト | 関数・モジュール単体が設計どおりに動くことを確認する | サービス層、リポジトリ層、ユーティリティ（処理設計書の関数） | 自動（Vitest。DBは fake-indexeddb） | 実装と並行して作成・実施 | `01_unit/単体テスト仕様書.md` |
| 結合テスト | 画面と処理・DBを組み合わせて、画面詳細設計書どおりに動くことを確認する | 画面（SC-01〜SC-08、ダイアログ）と処理（P-01〜P-10）の組み合わせ | 自動（React Testing Library＋fake-indexeddb）。PCのブラウザでの手動確認を補助的に行う | 各画面の実装完了時 | `02_integration/結合テスト仕様書.md` |
| システムテスト | 実機で、業務・機能シナリオと非機能要件を満たすことを確認する | アプリ全体（PWA として） | 手動（iPhone 実機。M-02 5章の方法でビルド結果を確認） | 全機能の実装完了後、公開前 | `03_system/システムテスト仕様書.md` |
| 受入テスト | 利用者（本人）が実際の服を登録して使い、目的を果たせることを確認する | 業務シナリオ（画面定義書 6.1 BS-01〜BS-05） | 手動（本番公開した版を実際に使う） | 1.0.0 公開後 | `04_acceptance/受入テスト結果.md` |

## 3. テスト観点

### 3.1 単体テスト

| 対象 | 主な観点 |
|------|---------|
| 入力チェック（itemValidator） | 必須項目の未入力、文字数の境界値（50文字・51文字等）、購入金額の境界値（0、9,999,999、10,000,000、小数・負数）、購入日の境界値（今日・明日）、前後の空白・全角空白のみの入力 |
| 保存用の値への変換 | 空文字が null になる、季節が春→冬の順に並ぶ、金額が数値になる |
| 絞り込み（listQuery.filter） | 各条件単独、項目内のOR、項目間のAND、「未設定」サブカテゴリ、条件なし |
| 並び替え（listQuery.sort） | 7種の並び順それぞれ、未入力が末尾になる、同値は登録日の新しい順、名前順で英字が日本語の後になる |
| 件数計算・ブランド一覧 | チップの件数が他の条件を反映する、ブランドの重複除去と並び順 |
| リポジトリ | 登録・更新・削除で items・photos・thumbnails がそろって変わる、途中で失敗したときにすべて取り消される、サブカテゴリの一意制約・30件上限・使用中の削除不可、表示順の入れ替え |
| 起動時処理 | 初期サブカテゴリが初回のみ投入される、すべて削除後に再投入されない、不正な並び順コードが初期値に戻る |
| 表示形式（format） | 日付・金額・件数・容量（1MB未満／MB／GB の境界） |

### 3.2 結合テスト

| 対象 | 主な観点 |
|------|---------|
| 画面の表示 | 項目の表示内容・形式、0件時・該当0件時の表示、未入力項目の「未入力」表示 |
| 画面の操作と遷移 | 画面遷移図（画面定義書 4章）の全遷移（TR-01〜TR-36） |
| 入力とエラー | エラーメッセージの表示位置・文言（メッセージID）、修正時にエラーが消える、最初のエラー項目へのスクロール |
| 状態の保持 | 絞り込み条件・並び順・スクロール位置の保持と初期化（SC-01 7章） |
| DBの変更の反映 | 登録・編集・削除・サブカテゴリ変更が他の画面に反映される |
| 例外処理 | DBの書き込み失敗時に MSG-E11 が出て入力内容が残る、存在しないアイテムを開いたときの MSG-E13 |

### 3.3 システムテスト（iPhone 実機）

| 区分 | 主な観点 |
|------|---------|
| 機能シナリオ | 画面定義書 6.2 の FS-01〜FS-06 を通しで実施 |
| カメラ・写真 | カメラ撮影、フォトライブラリからの複数選択、10枚の上限、縦向き・横向きの写真の向き、保存した画像に位置情報が含まれない（M-04 2.2） |
| PWA | ホーム画面への追加、ホーム画面からの起動（Safariの表示がない）、機内モードでの全機能の動作、未追加時の案内バナー |
| アプリの更新 | 新しい版の公開後に更新の案内が出る、「更新」で切り替わる、入力中は案内が出ない、更新後もデータが残る（M-01） |
| データの移行 | DB構造を変える版で、旧版のデータを入れた状態から更新して正しく移行される（該当する版のみ） |
| 性能 | 300件登録した状態で、一覧表示・絞り込みの結果表示が2秒以内（要件定義書 6章）。確認用データは `npm run seed:sample` で作成 |
| 容量 | 写真の保存容量が見積もり（DB設計書 共通 8章）の範囲に収まる、SC-06 の表示と一致する |
| データの保持 | アプリを閉じて開き直す、iPhone を再起動する、数日間開かない、の各場合にデータが残る |
| 画面の表示 | 対応するiOSの範囲、ノッチ・ホームバーとの重なりがない、文字の大きさの設定を変えても崩れない |

### 3.4 受入テスト
- 手持ちの服を実際に登録し（BS-02）、1〜2週間程度ふだん使いする
- 業務シナリオ BS-01〜BS-05 がそれぞれ問題なく行えたかを記録する
- 使っていて不便に感じた点は、不具合とは分けて「改善要望」として記録し、次の版で対応するか判断する

## 4. テスト環境

| 環境 | 内容 |
|------|------|
| 自動テスト | PC（Node.js 22系）、Vitest、jsdom、fake-indexeddb。GitHub Actions でも同じテストを実行する（M-03 4.1） |
| 実機テスト | 利用者の iPhone（iOS Safari）。PC の開発サーバーを HTTPS で公開して接続する（M-02 5章） |
| テストデータ | 単体・結合テストはテストコード内で作成。実機の性能テストは `npm run seed:sample`（300件、写真付き）で作成 |

- 実機テストは本番の公開URLでは行わない（本番データと混ざるため。M-02 5章）。受入テストのみ本番の公開URLで行う

## 5. 自動テストの基準

| 項目 | 基準 |
|------|------|
| 実行のタイミング | 作業ブランチへの push 時、main への取り込み時、公開時（M-03 4章） |
| 合格条件 | 全テストが成功すること。失敗したテストがある状態では main に取り込まない・公開しない |
| カバレッジ（網羅率） | サービス層・リポジトリ層・ユーティリティの行カバレッジ 80% 以上を目安とする。画面層は数値目標を設けず、3.2 の観点を満たすことを優先する |

## 6. 不具合の管理

### 6.1 重要度

| 重要度 | 定義 | 例 |
|-------|------|----|
| 高 | データが失われる・壊れる、アプリが使えなくなる、主要な機能（登録・一覧・詳細）が使えない | 保存したアイテムが消える、起動しない |
| 中 | 機能が設計どおりに動かないが、別の操作で回避できる | 絞り込み結果が誤っている、エラーメッセージが出ない |
| 低 | 表示の崩れ・文言の誤りなど、使用に大きな影響がない | 余白のずれ、誤字 |

### 6.2 記録と対応
- 不具合は、見つけたテストレベルの仕様書・結果のファイルに、テストケースと結びつけて記録する（番号、内容、重要度、対応状況）
- 修正後は、そのテストケースを再実施して確認する。関連する自動テストがない場合は追加する

## 7. 各レベルの完了条件

| レベル | 完了条件 |
|-------|---------|
| 単体テスト | 全テスト成功、カバレッジ基準を満たす |
| 結合テスト | 全テスト成功、画面遷移（TR-01〜TR-36）をすべて確認済み |
| システムテスト | 全テストケースを実施し、重要度「高」「中」の未解決の不具合が0件。「低」は残っていても公開してよいが、対応予定を記録する |
| 受入テスト | 業務シナリオ BS-01〜BS-05 がすべて行え、利用者（本人）が公開の継続を判断する |
